## Findings (severity-sorted)

### A9-01 · Severity: MAJOR
- **Location:** app/src/main/java/com/areenax/nativeapp/ui/screens/wallet/ConfirmWithdrawScreen.kt:278 · ui/screens/wallet/DepositConfirmScreen.kt:458 · ui/screens/info/AboutScreen.kt:454 · ui/screens/social/MyTeamScreen.kt:409 · ui/screens/profile/MyStatsScreen.kt:229
- **Steps to reproduce:** Enable light theme. Open Confirm-Withdraw footer ("By confirming, you agree to the risks & terms.", 11-12sp), Deposit-Confirm hint, About footer ("© … All rights reserved.", 14sp), My-Team note (11sp #94A3B8). Compute WCAG ratio of `onSurfaceVariant` composited at its `copy(alpha = …)` over the white/#F8F9FF surface.
- **Expected vs actual:** Expected ≥ 4.5:1 for normal-size text (WCAG 1.4.3 AA). Actual (arithmetic in a9-contrast.md): onSurfaceVariant #434655 @α0.7 on white = **2.67:1** (2.64:1 on bg); @α0.6 = **2.15:1**; hardcoded #94A3B8 on white = **2.56:1** (2.21:1 on lavender card); #434655 @α0.8 (MyStats) ≈ **3.4:1**. Dark theme versions pass (4.8-6.7:1). All four are 11-14sp normal text, below even the 3:1 large-text bar in three cases.
- **Root cause:** Secondary copy styled by fading the token color (`copy(alpha = 0.6-0.8f)`) instead of using a dimmer token; alpha compositing destroys the scheme's guaranteed contrast. One hardcoded raw gray (#94A3B8) outside the token system.
- **Proposed minimal fix:** Drop the alpha copies — use `onSurfaceVariant` at full opacity (7.6-9.4:1 light) or add a dedicated `muted` token with computed ≥4.5:1; replace #94A3B8 with `onSurfaceVariant`.
- **Regression risk:** low — color-only changes on non-action copy; design-token values untouched elsewhere (FFR: only these 5 lines' colors change).
- **Evidence:** audit/evidence/phase2/a9-contrast.md

### A9-02 · Severity: MAJOR
- **Location:** app/src/main/java/com/areenax/nativeapp/ui/screens/profile/ProfileScreen.kt:534-553 (ThemeSwitch, used :224-229) · ui/screens/auth/SignupStep3Screen.kt:467-527 (AgreementRow checkbox) · ui/screens/profile/AdminPanelScreen.kt:1307, 2302 (toggle pills) — and repo-wide: `rg 'toggleable|Role\.|stateDescription'` → 0 hits
- **Steps to reproduce:** Statically inspect the custom switch/checkbox: ThemeSwitch is a 40×24dp `Box.clickable` with no text, no contentDescription, no `Role.Switch`, no stateDescription, nested inside the clickable "Theme" MenuRow (two focus targets, inner one unlabeled). AgreementRow's 20×20dp checkbox has no `toggleable`, no checked-state semantics; its state gates the "Complete Account" button. AdminPanel on/off state is conveyed only by the `toggle_on`/`toggle_off` glyph (cd=null).
- **Expected vs actual:** Expected (WCAG 4.1.2 Name/Role/Value + TalkBack usability): a toggle exposes role + state ("checked/unchecked", "on/off") and one merged focus target. Actual: state is invisible to accessibility services; a TalkBack user cannot hear whether the signup agreement is checked (signup gate) or whether dark mode is on; switch is an unlabeled focus target.
- **Root cause:** Hand-drawn controls ported 1:1 from web CSS; Compose semantics layer never used (0 `semantics{}`, 0 `clearAndSetSemantics`, 0 `Role` in the whole codebase).
- **Proposed minimal fix:** On each control add `Modifier.toggleable(value = …, role = Role.Switch/Checkbox, onValueChange = …)` (merges descendants) on the row; remove the inner nested clickable; give AgreementRow a `contentDescription`/semantics state. ~4 sites.
- **Regression risk:** low — semantics-only; no visual/layout change; taps still work (`onValueChange` maps to existing handlers).
- **Evidence:** audit/evidence/phase2/a9-talkback-static.md

### A9-03 · Severity: MINOR

### A9-04 · Severity: MINOR
- **Location:** app/src/main/java/com/areenax/nativeapp/core/ui/AppBar.kt:119-127 (40dp AppBarCircleButton → back button on ~30 screens + BellButton), :144-145 (36dp Sm variant) · core/ui/BottomNav.kt:68 (56×40dp nav items) · ui/screens/profile/EditProfileScreen.kt:528-535 (24×24dp clickable Icon — worst) · ui/screens/profile/AdminPanelScreen.kt:2082 (28dp-tall SmallQuietChip) · ui/screens/social/ChatScreen.kt:317-337 (36dp emoji / 40dp send) · ui/screens/wallet/WalletScreen.kt? no — see evidence for the full 18-site table
- **Steps to reproduce:** Measure the clickable node of each cited site (modifier chain arithmetic in a9-touch-targets.md): e.g. EditProfile password toggle = the 24dp Icon itself is `.clickable`; AppBarCircleButton = `Surface(onClick).size(40.dp)`; BottomNav tab = `Box.size(56.dp, 40.dp).clickable`.
- **Expected vs actual:** Expected ≥48×48dp (Material/AOSP touch-target guidance). Actual: 18 distinct sites between 24-40dp; systemic components put affected instances at 60+ (back/bell on ~30 screens, 5-6 nav tabs everywhere, auth toggles, chat send). All still ≥24dp, so WCAG 2.5.8 AA is technically met — this fails Material guidance, not AA.
- **Root cause:** Web px-equivalents ported literally (w-10 = 40dp, p-2+20dp glyph = 36dp) without target-size expansion.
- **Proposed minimal fix:** Expand hit targets without changing visuals: `Modifier.minimumInteractiveComponentSize()`/48dp touch bounds via `Modifier.touchTargetExpansion()`-style padding + negative spacing, or swap Icon-clickables for sized IconButtons. Start with EditProfile toggle (24dp), SmallQuietChip (28dp), AppBar/BottomNav.
- **Regression risk:** med — enlarging hit areas can introduce overlap/misclicks in dense rows (chat input, AppBar); needs visual QA per screen after fix.
- **Evidence:** audit/evidence/phase2/a9-touch-targets.md

### A9-06 · Severity: MINOR
- **Location:** app/src/main/java/com/areenax/nativeapp/ui/screens/profile/AdminPanelScreen.kt:2082 (28dp chip + 12sp label), :2041, :1262 (36dp chips) · ui/screens/auth/SignupStep3Screen.kt:268 (40dp "Go to Login" pill) · ui/screens/profile/ProfileScreen.kt:441 (44dp HeaderPillButton) · 20× h-12/48dp buttons repo-wide
- **Steps to reproduce:** Static scan: `.height(N.dp)` with a `Text(` in the same block → 82 sites in the 8-48dp band (mostly Spacers; real text-rows tabled in a9-font-scale.md). At 2.0× font scale a 12sp label renders ~24-28sp tall inside a 28dp-clipped Surface; 14sp in 36-40dp rows likewise.
- **Expected vs actual:** Expected: text rows grow with font scale (or use heightIn(min=…)) so 1.3-2.0× does not clip. Actual: 28-44dp fixed-height rows clip/overflow at 2.0×; 48dp buttons are descender-tight; only the 56dp+ rows are safe. lineHeights are sp (scale correctly; no dp line-height exists) — the clipping comes from the row heights, not the text.
- **Root cause:** Web `h-7/h-10/h-11/h-12` heights ported as fixed `.height()` instead of min-height (only 14 `heightIn` sites exist).
- **Proposed minimal fix:** Convert text-bearing rows ≤44dp to `heightIn(min = N.dp)`; keep exact visuals at 1.0× (min-height = same value).
- **Regression risk:** low — identical rendering at default font scale; rows may grow only at large scales. (Runtime rendering NOT VERIFIED — no device.)
- **Evidence:** audit/evidence/phase2/a9-font-scale.md
