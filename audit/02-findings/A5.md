**ID: A5-01 · Severity: MINOR · Location: app/src/main/java/com/areenax/nativeapp/core/network/ApiResult.kt:66-69 (and every toast that renders `res.message`)**
Steps to reproduce (static; runtime = NOT VERIFIED, no staging server): turn off connectivity (or point `app_base_url` at a dead host), then use Login (LoginScreen.kt:389-390), Wallet load (WalletScreen.kt:172-179), Deposit (DepositConfirmScreen.kt:206-210), Transfer (TransferScreen.kt:168-172), Chat send (ChatScreen.kt:139-145) — each shows `res.message` inside the toast description.
Expected vs actual: expected a user-appropriate "No connection / timed out" style message; actual for `IOException` with a non-blank message the **raw OS exception text is shown verbatim**: OkHttp/Java emits e.g. `timeout` (SocketTimeoutException), `Unable to resolve host "YOUR-AREENAX-DOMAIN.example.com"` (UnknownHostException), `Failed to connect to …` (ConnectException), SSL handshake text — `safeCall` maps `IOException → NetworkError(e.message!!)` (ApiResult.kt:67) and falls back to the friendly default only when the message is blank (`DEFAULT_NETWORK_MESSAGE`, ApiResult.kt:24). The catch-all `Exception → Error(e.message)` (ApiResult.kt:69) likewise surfaces raw kotlinx-serialization text (e.g. `Unexpected JSON token at offset…`) when a 2xx body fails to decode. HTTP-status errors are handled well: `extractErrorMessage` (ApiResult.kt:35-49) shows the server's `error` field or "Request failed (status)" — matching the web (`src/lib/api.ts:86-88`).
Root cause: message-selection delegates to exception `.message` instead of mapping exception types to user copy.
Proposed minimal fix: in `safeCall`, branch on exception type: UnknownHostException/ConnectException/SocketTimeoutException/SSLException → fixed friendly copy (keep the raw detail in a log), keep `DEFAULT_NETWORK_MESSAGE` for blank messages; in the catch-all, replace `e.message` with "Something went wrong" unless the exception is a known user-facing type. Single-point change, all 42 NetworkError branches inherit it.
Regression risk: low — one helper, message text only, no control-flow change; web shows comparable raw browser text ("Failed to fetch"), so this is a deliberate small divergence.
Evidence: audit/evidence/phase2/a5-network-core.md §4; a5-offline.md §7.

**ID: A5-02 · Severity: MINOR · Location: app/src/main/java/com/areenax/nativeapp/core/network/ApiClient.kt:41-46**
Steps to reproduce: inspect `OkHttpClient.Builder()` — no `connectTimeout/readTimeout/writeTimeout/callTimeout/retryOnConnectionFailure` is ever set (verified by full read; also grep across `core/network` = 0 hits).
Expected vs actual: expected explicit, documented timeouts (or a deliberate decision to keep library defaults); actual: okhttp 4.12.0 defaults apply implicitly — connect 10s, read 10s, write 10s, **callTimeout 0 (no overall cap)** and **retryOnConnectionFailure true** (silent transport-level retry when the request was not yet transmitted — replay risk bounded by the server's Idempotency-Key dedupe; the client itself sends a fresh UUID per non-GET, ApiClient.kt:77-88). Consequence visible in app flow: with a black-holed (not RST-ing) network the AppShell splash waits for the restored-token `GET /me` for the full 10s read timeout before clearing (AppShell.kt:92-106, gate :141); nothing can hang longer than one 10s read, but total call time is unbounded for trickling responses.
Root cause: defaults left implicit; intent not recorded anywhere (no comment/constant).
Proposed minimal fix: add explicit `.connectTimeout(10, SECONDS).readTimeout(15, SECONDS).writeTimeout(20, SECONDS).callTimeout(30, SECONDS).retryOnConnectionFailure(true)` + comment; tune write up for ≤8 MB base64 uploads on slow uplinks (regression checked with a real device — NOT VERIFIED here).
Regression risk: low (config-only) — but values affect real upload paths, so verify on device before shipping.
Evidence: audit/evidence/phase2/a5-network-core.md §1.

## 2. DELIVERABLE 1 — NETWORK RESILIENCE

**Timeouts/retries (ApiClient.kt:41-46):** NO explicit config. OkHttp 4.12.0 defaults: connect/read/write 10s each, callTimeout disabled, `retryOnConnectionFailure=true` (OkHttp-internal, pre-transmission only). No application retry/backoff interceptor; the four interceptors are auth-token, idempotency-key, double-submit guard (409 locally, ApiClient.kt:95-112), and 401→logout. See A5-02.

**Failure mapping (`safeCall`, ApiResult.kt:55-70):**
| Failure | Mapping | Message shown to user | Citation |
|---|---|---|---|
| Double-submit guard trip | `Error("Request already in progress", 409)` | that string (raw) | ApiResult.kt:57-58, :29 |
| HTTP 4xx/5xx (`HttpException`) | `Error(extractErrorMessage(code, body), code)` | server `error` field, else `"Request failed (status)"` — web-parity (api.ts:86-88) | ApiResult.kt:59-65, :35-49 |
| Offline / DNS / timeout / reset (`IOException`) | `NetworkError(e.message!! if non-blank)` | **raw exception text** (`timeout`, `Unable to resolve host …`), else `"Network error. Please check your connection."` | ApiResult.kt:66-67 (A5-01) |
| Malformed 2xx JSON / any other exception | `Error(e.message)` | **raw** kotlinx-serialization text, else "Something went wrong" | ApiResult.kt:68-69 (A5-01) |
| HTTP 401 (any) | response still returned to safeCall AND `onUnauthorized` fires: session wipe + Login, stack cleared | per-screen toast | ApiClient.kt:114-123; AreenaxApplication.kt:72-75; SessionManager.kt:197-217; AppNavigator.kt:94-101 |

**Repeated-failure / toast-loop (A1 F-13 verify+expand):** NO toast loop exists — all automated pollers are silent on failure (Chat 3s, MyTournaments 30s, unread 30s-throttled), the toast system holds exactly one toast (TOAST_LIMIT 1), and one-shot loads toast once per screen mount (LeaderboardScreen.kt:84-111 is `LaunchedEffect(Unit)`, not a loop). Residual: fixed-cadence polling with no backoff and no logging during outages (A5-07). Poll backoff: **none anywhere** (A5-07).

## 3. DELIVERABLE 2 — OFFLINE BEHAVIOR

- **Detection:** ConnectivityManager `NetworkCallback` (registerNetworkCallback, ConnectivityObserver.kt:43-52) with `NET_CAPABILITY_VALIDATED` required (onCapabilitiesChanged :37-40; currentlyOnline :62-67); permission ACCESS_NETWORK_STATE (manifest :6). Callback lifecycle bound to composition (AppShell.kt:86-89).
- **Gate:** loss → `navigate(offline)` pushed (AppShell.kt:121-125, duplicate-push guarded); regain → auto-pop `goBack()` (AppShell.kt:126-128) = **REQ-057 auto-recovery VERIFIED statically**; OfflineScreen additionally recovers on mount if already online (OfflineScreen.kt:68-70) and its "Try again" button pops when online, else toasts "Still offline" (:132-145).
- **Mid-flow:** form screens are disposed while offline (AnimatedContent single-screen projection) and their `remember` state is lost on the pop-back → typed input (amounts, message drafts, host form) is gone (A5-06). Mutations in flight fail with a destructive toast naming the action ("Deposit failed", DepositConfirmScreen.kt:206-210); no silent money-path failures.
- **DataStore offline:** hydration is a pure local read (SessionManager.kt:64-73) → **session restore offline works**: token+user come back from disk; the restore-time `GET /me` (AppShell.kt:92-106) only *overwrites* on Success and only *wipes* on 401 — a NetworkError keeps the cached session and ends the splash (`checked=true`, :105). Auth gate leaves the restored user in place (user != null ⇒ gate passes).
- **Blind spot:** the gate covers airplane-mode only; a *reachable* network with a dead/5xx-ing server never trips it — per-request toasts + the A5-03 false-404 state are the only signals (A1 F-13 still stands for this case).

**IDOR answer — can user A read user B's data? NO.** Every read and write of user-owned data on every endpoint in the matrix is keyed to the x-token session (`where userId: user.id`, `tournamentId_userId {userId: user.id}`, owner/receiver/sender equality checks, pairwise message scoping) — no route the app calls trusts a client-proposed ID to select *another* user's records (notifications PATCH/DELETE with foreign ids are no-ops, notifications/route.ts:51-54,72-74). The only client-ID-trusting surfaces are benign-or-minor: chat target without friendship check (A5-04, pairwise-scoped so no cross-read), and the uid lookups exposing semi-public profile fields incl. `fullName` unthrottled (A5-05). Admin routes are uniformly RBAC-gated server-side even though the native client gate is only cosmetic. Caveat: this is static analysis only — runtime enforcement on a live server is NOT VERIFIED.
