### Findings

**ID: A12-01 · Severity: MAJOR · Location: `app/src/` (no `test/`, no `androidTest/`), `app/build.gradle.kts:50-77`, `gradle/libs.versions.toml` (whole file)**
- Steps to reproduce: `ls app/src` → only `main`; grep gradle files for `testImplementation|junit|robolectric|ui-test` → 0 hits.
- Expected vs actual: A real-money app (wallet deposit/withdraw/transfer, admin ops) shipping to Play should have at least a JVM unit-test tier for its parity-critical pure logic; actual = the only automated check that ever ran on this codebase is the Kotlin compiler (Phase 0) and one-time icon-geometry script.
- Root cause: native port was built agent-style in one pass with a 1:1 web-port mandate; tests were never in scope, and the Phase-0 reality (319 compile errors, first APK only on 2026-09-20) means no test could even have executed before that date.
- Proposed minimal fix: add `testImplementation` tier only (JUnit 4, kotlinx-coroutines-test, OkHttp MockWebServer, Robolectric optional) and the P0 test classes in the table below. No `androidTest` until a device exists.
- Regression risk: low — test-only deps and a new source set cannot change release bytecode (R8 consumes `main` only).
- Evidence: `audit/evidence/phase2/a12-part1-test-infra.log`, `a12-part1-gradle-ci-web.log`

**ID: A12-02 · Severity: MAJOR · Location: repo roots (`/home/z/my-project`, `AreenaxNativeAndroid/`) — no `.github/`, no `.gitlab-ci.yml`**
- Steps to reproduce: `find` both roots for CI configs → absent everywhere; web `package.json` has no `test` script either.
- Expected vs actual: even `./gradlew :app:compileReleaseKotlin testReleaseUnitTest` on a schedule/PR hook would have surfaced the 319-error state on day one; actual = nothing re-validates the tree between owner sessions.
- Root cause: single-operator sandbox workflow; builds are run manually by agents.
- Proposed minimal fix (no code): a 1-job CI (or even a `tools/check.sh`: `gradlew compileReleaseKotlin + :app:test + verify_visual.mjs`) wired to whatever repo host the owner uses; exact host unknown in sandbox.
- Regression risk: low (process-only; zero app-code touch).
- Evidence: `audit/evidence/phase2/a12-part1-gradle-ci-web.log`, `a12-part1-web-tests.log`

**ID: A12-03 · Severity: MAJOR · Location: `core/network/ApiClient.kt:65-123`, `core/session/SessionManager.kt:38-42`, `AreenaxApplication.kt:32-63` — ServiceLocator coupling blocks the highest-value tests (A1 F-3 dependency)**
- Steps to reproduce: try to unit-test `AuthInterceptor` in a JVM test → it needs a concrete `SessionManager`, whose constructor needs an Android `Context` (DataStore delegate `SessionManager.kt:40`); try to fake `Api` → `NavEnv`/`AreenaxApplication` wire concrete types only (no interfaces); `ApiClient.onUnauthorized` (`ApiClient.kt:36-37`) and `SettingsCache.cached/inflight` (`SettingsCache.kt:20-23`) are process-global mutable state that leaks between tests.
- Expected vs actual: the four cross-cutting request rules (x-token, Idempotency-Key, in-flight guard, 401→logout) are exactly the logic a MockWebServer unit test verifies in minutes; actual = untestable by construction.
- Root cause: deliberate 1:1 web-port trade-off (module singletons ≙ zustand/store.ts), per A1 F-3 — "directly causes F-2".
- Proposed minimal fix (PROPOSED ONLY — NOT IMPLEMENTED, owner gate): extract one interface `interface TokenProvider { val token: StateFlow<String?> }`, have `SessionManager` implement it, change `AuthInterceptor(sessionManager: SessionManager)` to `AuthInterceptor(tokens: TokenProvider)` (2-line call-site change in `ApiClient.create:39-46`). Optionally make `UnauthorizedInterceptor`'s callback injectable (`ApiClient.onUnauthorized` already is — it just needs reset-in-@After discipline in tests). This single seam unlocks the whole money-path tier (P0-3 below) plus a fake-`Api` seam if `NavEnv.apiProvider` (already a lambda, `NavEnv.kt:39`) is reused in tests.
- Regression risk: **low-med** — the refactor is behavior-preserving (same StateFlow read, `ApiClient.kt:67`), but it touches the auth header path of every request; mitigate with the new MockWebServer tests themselves (they become the regression net) + FFR freeze review of the diff.
- Evidence: `audit/evidence/phase2/a12-part2-targets.log`, `a12-part3-cost.log`

**ID: A12-04 · Severity: MINOR · Location: `core/util/Formatters.kt:132-137` (maskAccountNumber), `core/util/QrPayload.kt:28-55` (strict parse), `core/util/TournamentState.kt:26-46` (nowMillis-injectable status machine), `core/network/ApiResult.kt:34-46` (extractErrorMessage) — the app's entire web-parity layer has no golden tests**
- Steps to reproduce: none possible — no test source set exists.
- Expected vs actual: these classes are documented as "EXACT Kotlin port of src/lib/qr.ts / api.ts / tournament-state.ts"; parity regressions (masking, QR grammar, date formatting, countdown, status flips, error-message extraction) are currently detectable only by eyeball; actual = zero executable proof of "exact".
- Root cause: no test infra (A12-01); the functions themselves are pure and cost nothing to test.
- Proposed minimal fix: golden-value unit tests transcribed from the web sources (see P0-1/P0-2/P1-6 in the plan).
- Regression risk: low (test-only).
- Evidence: `audit/evidence/phase2/a12-part2-targets.log`

**ID: A12-05 · Severity: MINOR · Location: validation sites `ui/screens/auth/SignupStep2Screen.kt:101-103` (password rules), `SignupStep3Screen.kt:454` (EMAIL_REGEX), `LoginScreen.kt:415-416` (phone regexes) — client-vs-server validation parity is untested and untestable until A4 maps the matrix**

**ID: A12-06 · Severity: MINOR · Location: `ui/screens/**` (48 screen files, 46 route keys `core/nav/ScreenKeys.kt:10-67`) — no Compose UI smoke tests; full per-screen coverage is neither feasible nor needed; blocked by NavEnv/Context graph (A12-03)**

### Sampling rationale for the 48 screens (P2 tier)
48 screens ÷ 5 clusters: money (7), auth (6), social/QR (8), tournament (5), admin/profile (22). P0/P1 already covers all pure logic; the Compose tier samples the cluster whose failure costs money first (cluster 1 + guest gates), then admin (2,346-LOC AdminPanelScreen per A1 F-4 = highest change-ripple), then the long tail becomes a cap-25-nav + generic smoke instead of per-screen work.

### Minimal ServiceLocator refactor that unlocks the most (PROPOSED, NOT IMPLEMENTED)
One seam — `TokenProvider` interface implemented by `SessionManager`, consumed by `AuthInterceptor` (A12-03 above). Two alternatives considered and rejected: (a) full DI framework (Hilt/Koin) — high regression surface across 48 screens, contradicts the 1:1-port freeze; (b) test-only subclass of SessionManager — impossible, `Context`-bound in constructor and `preferencesDataStore` delegate. Regression risk of the chosen seam: low-med (touches auth-header path of every request; mitigated by the P0-3 tests the seam itself enables + FFR diff review). Nothing was implemented; owner gate required.

## PART 3 — COST OF ZERO TESTS (concrete bugs a test tier would have caught)

1. **319-compile-error era (2026-09-19 probe).** `compile-probe-run1-2026-09-19.log`: 319 `e:` lines across **52 distinct .kt files** (recounted from the log in `a12-part3-cost.log`); trajectory 319→94→42→2→0 (worklog Tasks 8-9). The app had never been assembled in its history before TASK-004. Any CI compile gate — the cheapest possible "test" — would have caught every one of the 7 root causes (×136, AreenaxSpinner ×65, charAt ×8 Java-isms, etc.) at introduction time, instead of a 4-session triage campaign. Not one of these was a logic bug a human could have missed — they were machines-catchable by definition.
2. **REQ-058 param-less unread poll (RTM.md:110, conflicts #10, Q6).** `Api.kt:239-241` declares `unreadCount(): GET notifications` **without** the `countOnly=1` query the SPEC/00 §2e contract mandates (the query variant exists at Api.kt:236-237 but is unwired for polling; `UnreadManager.kt:32-48` calls `unreadCount()`). A one-line MockWebServer assertion ("poll request URL must contain `countOnly=1`") pins this permanently — the bug class is "request-shape drift vs web", precisely what P0-3 exists to catch.
3. **REQ-143 upload-cap inconsistency (RTM.md:201, conflicts #11/#12, Q2/Q3).** Web **rejects** over-cap uploads with exact copy; native silently downscales and `compressToCap`'s last resort (`PhotoPickers.kt:87-91`) returns an **unverified-size** payload; the 4 MB `UploadCaps.RESULT_PROOF` (`PhotoPickers.kt:31-36`) is wired only in a dead sheet while the live path uses 8 MB (`TournamentDetailsScreen.kt:114-115`). A unit test over `compressToCap` with a pathological bitmap ("output ≤ cap OR explicit reject") fails today — which is the point: this is real-money upload-path behavior divergence that no human eyeball caught across three phases of manual testing.
4. **REQ-008 dropped params (RTM.md:60, conflicts #3, Q5).** Post-QR flow navigates with `{qrUser}`/`{qrTeam}` (`AppShell.kt:220-235`) but both destinations have **0 `env.params` reads** (FriendsScreen.kt / MyTeamScreen.kt, Attacker 10-f grep) — payload consumed then discarded; web opens Add-Friend/Team-Connect popups. A navigation-machine test asserting "navigate(FRIENDS, params) → currentParams reachable by destination" (P0-4 family) plus a route-contract test would have flagged the orphaned params the same day the divergence was coded.
5. **Meta-cost:** the RTM test column records `none (no automated tests in repo)` on **122 of 165 rows** (`a12-part3-cost.log`) — every one of those rows currently costs a manual device run to re-verify, which has never happened (no device in sandbox; Phase-0/1 record). Each PART-2 test converts a standing manual-verification debt into a machine check.
