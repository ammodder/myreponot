## A13-01 · Severity: BLOCKER · Location: app/src/main/res/values/strings.xml:11

**Steps to reproduce.** Read `strings.xml:11`: `<string name="app_base_url"
translatable="false">https://YOUR-AREENAX-DOMAIN.example.com</string>`. Read
`AreenaxApplication.kt:66` (`val baseAppUrl: String by lazy { getString(R.string.app_base_url) }`)
which feeds every Retrofit call (`:49` `ApiClient.create(baseAppUrl, session)`) and the NavEnv
(`:59`). Build anything — the placeholder ships in every APK/AAB variant with no build-time
warning or failure.

**Expected vs actual.** Expected: a release artifact carries the live AREENAX domain (README.md:24
"STEP 1 — set your server URL (the only required change)"). Actual: the artifact would resolve
every API call, QR deep link and image URL against a non-existent `.example.com` host →
universal `NetworkError` toasts, home renders empty, deposit/withdraw/login all dead. Nothing in
Gradle or code fails the build when the placeholder is left in.

**Root cause.** The URL is a deploy-time string resource with a placeholder default; the project
deliberately keeps it editable-in-one-place (README STEP 1) but has no enforcement (no
startup assertion, no build-config injection) — exactly as flagged in A1 F-1 (graded MAJOR there
as code-health; in the A13 rollout frame it is *the* gate, hence BLOCKER here).

**Proposed minimal fix.** Before generating any release bundle: replace the placeholder with the
live domain (same origin as the web panel, per strings.xml:5-10 comment). Minimal guard in the
fix phase (owner-approved): fail fast at startup or build time when the URL still contains
`YOUR-AREENAX-DOMAIN` (e.g. a unit test or `check()` in AreenaxApplication.onCreate), or inject
via `buildConfigField`/`-P` property instead of a hand-edited resource.

**Regression risk: low.** One string change + optional guard; the value already flows through a
single lazy property, no other call sites. Risk is only in *forgetting* it — which is the finding.

**Evidence:** audit/evidence/phase2/a13-rollout-facts.md §4 (strings.xml + README STEP 1 cite);
audit/02-findings/A1.md:220 (F-1); AreenaxApplication.kt:49,59,66.

## A13-02 · Severity: MAJOR · Location: app/build.gradle.kts:50-77 (dependency block) — absence

**Steps to reproduce.** (1) `rg -in "firebase|crashlytics|acra|sentry|bugsnag" app/ gradle/`
→ only substring false-positives (`hasEntry` contains "sentry"); zero SDK/import/manifest
references (a13-grep-crash-reporting.log). (2) `rg -in
"uncaughtexceptionhandler|defaultuncaught" app/src` → 0 hits: not even a local
`Thread.setDefaultUncaughtExceptionHandler` exists. (3) The dependency block
(app/build.gradle.kts:50-77) and gradle/libs.versions.toml:1-46 contain exactly the REQ-142
frozen allowlist (Compose/Core/Coil/Retrofit/OkHttp/kotlinx-serialization/DataStore/ZXing) — no
crash/telemetry library of any kind.

**Expected vs actual.** Expected (rollout-readiness standard): a production app has at least a
baseline crash/ANR signal so the owner learns of field failures. Actual: **zero crash telemetry**
— if the release crashes in the field, nobody finds out except via user complaints/Play reviews.

**Root cause.** REQ-142 freezes the dependency allowlist with NO Firebase/analytics/trackers and
REQ-059 makes push/telemetry additions ask-first; no alternative crash channel was ever chosen.

**Decision table (REQ-142-constrained):**

| Option | Effort | Privacy | Needs server? | Fits allowlist? |
|---|---|---|---|---|
| **Google Play vitals (zero-integration)** — ANR+crash rates auto-collected by Play Console for any published app | **Zero code**, zero dep; data appears after real install base accrues | Governed by Google Play terms; no in-app data collection, no new permission | No (Play infra) | **YES** — no dependency, no code, no manifest change |
| ACRA (HTTP→own endpoint or email/app) | Small: 1 dependency + ~10-line init; attachment/polish extra | Self-controlled (own server or inbox); report contents configurable (strip device/PII fields) | HTTP mode: yes (own backend); email mode: no server but embeds SMTP creds in app (bad) | Gray — new dependency not in the frozen list → owner ask-first ruling (REQ-059/142) |
| Sentry self-hosted | Medium-high: SDK dep + config + ops burden (self-host stack: web/postgres/redis/…) | Self-controlled; DSN shipped in app | Yes (dedicated server) | Gray — new dep **and** sequencing conflict: Q17 defers all server audit to after release |
| Local crash capture → user-initiated share (UncaughtExceptionHandler → file → share via existing SupportFab/WhatsApp channel) | Small-medium: ~1 handler file, no network code | Fully local; user consents by sending (privacy-friendly) | No | **YES** — zero new dependencies (pure platform API) |

**Proposed minimal fix.** Adopt **Play vitals as the baseline** (zero integration, zero allowlist
impact — it is the minimum viable path given Q17 defers the server audit): publish, then read
Android vitals in Play Console (crashes, ANRs, wakeups). If the owner wants pre-Play-data crash
visibility, the allowlist-clean option is the local uncaught-exception handler with
user-initiated share; ACRA/Sentry only as a post-release owner decision (new dependency =
ask-first per REQ-059/142). No code change in Phase 2.

**Regression risk: low** (recommended path adds nothing to the app). The residual risk of NOT
doing it: MAJOR — silent field failures with no diagnostic channel (compounds A1 F-11/F-13).

**Evidence:** audit/evidence/phase2/a13-grep-crash-reporting.log (all greps + dependency block);
audit/01-requirements/REQUIREMENTS_LEDGER.md:185 (REQ-142), :165 (REQ-127 n/a), ledger REQ-059 row.

never paste keystore secrets into chat/audit docs (MISSING-INPUTS.md:18); (3) back the keystore
up offline — losing it without Play App Signing means the app can never be updated again under
`com.areenax.nativeapp`; (4) the sandbox `assembleRelease` (wave 2) stays unsigned — signing is
by design not reproducible here.

**Regression risk: med.** Signing itself is zero-code, but a botched first upload (wrong key
enrolled, keystore lost, or password-protected zip lost) is unrecoverable without Google support
— the one-time enrollment deserves double care.

## A13-04 · Severity: MINOR · Location: app/build.gradle.kts:16-17

**Steps to reproduce.** Read `versionCode = 2` (:16) and `versionName = "2.0.0"` (:17) — frozen
release identity per REQ-061 (RTM.md:86) and confirmed by aapt2 badging of the built APK
(worklog Task 9; assembleDebug-run2 evidence). Compare with owner decision **Q11-PREFER-1.0.0**
("try 1.0.0; if blocked use 2.0.0", STATE.md:104-105) and the server-driven About version
`AboutScreen.kt:110` (`settings?.version ?: "1.2.0"`, fallback per web parity; owner gate C4).

**Analysis — can 1.0.0 still be used? YES.** Play's monotonic-versionCode rule applies **per
applicationId, only to what Play has seen**: versionCode values are consumed by uploading/serving
a release on Play. The v2.0.0 debug APK published to the project website (/downloads/) is a
website download, **not a Play upload** — it consumes nothing. No artifact with this
applicationId has ever been uploaded to Play Console (app not on the store). Therefore
`versionCode = 1` / `versionName = "1.0.0"` is fully available for the FIRST Play upload; no
conflict, no workaround. Once the first Play release exists, versionCode becomes
monotonically-increasing forever (see A13-07 rollback rules), so this choice is only free until
first upload.

**What must change to ship as 1.0.0 (exact list, all fix-phase):**
1. `app/build.gradle.kts:16` → `versionCode = 1`; `:17` → `versionName = "1.0.0"`.
2. `AboutScreen.kt:110` fallback `"1.2.0"` → align with the shipped version (e.g. `"1.0.0"`), or
   hide the version row when `settings.version` is blank (C4 ruling covers this; keeping "1.2.0"
   would show three different numbers across gradle/server/offline states).
3. **Server-side: `settings.version` must be set to "1.0.0"** by the admin (the admin panel
   Version field, AdminPanelScreen.kt:337-341 placeholder "1.0.0", writes exactly this) —
   otherwise the About screen shows the server's value and the story splits again.
4. Play release notes / store listing should state the same version story.

If the owner instead stays on 2.0.0 (Q11 fallback), change nothing in gradle; only fix (2)/(3)
still apply to make the three version surfaces agree.

**Expected vs actual.** Expected: one coherent version story across gradle identity, server
`settings.version`, and About fallback. Actual: three independent values (2.0.0 / server-config
/ "1.2.0") that can disagree simultaneously.

**Root cause.** Version display is server-driven by design (web parity, REQ-127/151 family);
gradle identity and the fallback literal were never tied to Q11.

**Proposed minimal fix.** Decide Q11 at fix-phase start (before the first Play upload — it is
free now, expensive later): apply the 3-item list above; add no logic.

**Regression risk: low** — two one-line edits + one admin-panel entry, all before first upload;
only risk is touching versionCode AFTER a Play release exists (must never decrease).

**Evidence:** audit/evidence/phase2/a13-rollout-facts.md §1, §3, §5; RTM.md:86 (REQ-061);
STATE.md:104-105 (Q11), :118-120 (C4); AboutScreen.kt:110; AdminPanelScreen.kt:339.

## A13-07 · Severity: NOTE · Location: app/build.gradle.kts:21-34 + Play mechanics (external)

**Facts assembled for rollout (all verified as far as static analysis allows; store-facing
behavior NOT VERIFIED — no Play Console access):**

1. **AAB, not APK.** Play requires the Android App Bundle for NEW apps; the only built artifact
   is an APK (debug; release never assembled). Feasibility: bundle command is
   `./gradlew bundleRelease` (NOT executed per task rules); R8/minify already configured
   (build.gradle.kts:24-25), so the bundle task uses the same pipeline. Toolchain supports it
   (AGP 8.7.3, libs.versions.toml:2; builds run post-RAM-fix).
2. **R8 mapping retention.** Release minify is ON → every release build produces
   `app/build/outputs/mapping/release/mapping.txt` (standard AGP output path; **NOT VERIFIED**
   — no release build has ever run here, REQ-145/A1 F-16). Without keeping mapping.txt per
   release, Play vitals stack traces are obfuscated gibberish; upload it in Play Console (or use
   the Play App Signing deobfuscation file page) **per release**, named/archived by versionCode.
3. **Staged rollout plan → Play Console steps:** Internal testing (up to 100 testers, minutes to
   live) → Closed testing (owner's 14 testers; email-list track) → Open testing (optional) →
   Production with staged rollout percentages (e.g. 10% → 50% → 100%). Release notes/changelog
   go in each release's "Release notes" field per language in Play Console (there is no in-app
   changelog resource — strings.xml holds only app_name + app_base_url).
4. **Rollback rules (document, not testable):** "Halt staged rollout" (Production → Releases →
   Halt) only stops NEW users/devices from receiving the bad build — users who already got it
   keep it, and Android itself refuses a downgrade install (lower versionCode over higher). A
   versionCode, once served in a started release, is consumed: you **cannot re-upload the same
   versionCode after halting**; the only path is **roll forward** (fix + higher versionCode) —
   or, for a build never served to anyone, remove/deactivate it before the release starts.
   Practical consequence for Q11: treat versionCode as write-once from the first Play upload.
5. **minSdk 24 / targetSdk 35 breadth.** minSdk 24 = Android 7.0 (2016)+ — covers the practical
   entirety of active Play devices (exact device-mix % NOT VERIFIED). targetSdk 35 satisfies the
   current Play target-API policy window (policy quotes collected in
   audit/evidence/phase2/policy-research.md — A11 owns policy detail); compileSdk 35 matches
   (build.gradle.kts:10). Manifest is minimal (INTERNET+CAMERA+ACCESS_NETWORK_STATE only,
   REQ-141) — no permission-gating surprises for rollout.

**Root cause / fix:** informational — no defect. Carry items 1-2 into the release checklist and
the fix-phase release build.

**Regression risk: low.**

**Evidence:** audit/evidence/phase2/a13-rollout-facts.md §7; audit/evidence/phase2/policy-research.md
(target-API quotes); build.gradle.kts:10,21-34; strings.xml (full read, 12 lines).
