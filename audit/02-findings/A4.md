## DELIVERABLE 3 — INPUT SANITIZATION

- **No HTML/Markdown parsing anywhere** (`rg fromHtml|Html.|Markdown` = 0 hits) — Compose renders plain
  `Text`; server strings only reach UI as toast/body text. Safe by construction.
- **Number parsing is uniformly null-safe**: 42 `toDoubleOrNull/toIntOrNull/toLongOrNull` sites, all with
  `?:` fallbacks or null checks; **zero `!!` parses**. The amount pads build raw digit strings
  (DepositScreen.kt:80-92), so `toDoubleOrNull` can only fail on the "0" base — handled.
- **Locale**: output formatting pinned to `Locale.US` (Formatters.kt:15-35, matching web locale-stable
  output); no input is ever parsed from grouped/decimal-formatted text — no DecimalFormat-comma risk.
- **Trusting server strings**: `extractErrorMessage` (ApiResult.kt:35-49) safely JSON-parses `error`.
  Residual risk = 4 **message-text locks** where client behavior branches on English server substrings
  ("already submitted", "insufficient", "email", "admin") → A4-11. Server already sends structured flags
  (`alreadySubmitted:true`, `field:` keys) the client could use instead.
- **Server-side image sanitization is strong everywhere EXCEPT `/tournaments/[id]/result-proof`**, which
  accepts `data:image/`-prefixed payloads up to 5.5M chars and stores them RAW (no magic-byte sniff /
  re-encode — result-proof/route.ts:22-27, :64-69) — the one upload route that skips
  `validateAndReencodeImage` → A4-08 (server-side item, flagged for the owner's server fix phase).

### A4-01 · Severity: MAJOR
- **ID:** A4-01
- **Location:** server `/home/z/my-project/src/app/api/me/route.ts:65-72` (password change, no policy call);
  doc contradiction `src/lib/password-policy.ts:5-7`; client rule `EditProfileScreen.kt:238-243`
- **Steps to reproduce:** PATCH /me `{currentPassword: <correct>, password: "a"}` with a session token → 200,
  password replaced. (Any authenticated client; native UI allows it via the 6-char rule.)
- **Expected vs actual:** expected — password change enforces the signup policy (min 10, letter, number/special,
  breached list) exactly as password-policy.ts:5-7 claims ("used by BOTH signup and password change");
  actual — `/api/me` hashes `body.password` with zero validation. Client offers only ≥6 chars, so the two
  layers disagree (10 vs 6 vs ∞).
- **Root cause:** `validatePassword` was wired into register + setup/super-admin only; the /me PATCH route
  predates/forgot it while the policy docstring asserts both call sites.
- **Proposed minimal fix:** in me/route.ts before `data.password = hashPassword(...)`: run
  `validatePassword(String(body.password))` and 400 with `policy.errors[0]`. (Fix-phase, server side;
  native needs no change — server messages already toast verbatim.)
- **Regression risk: low** — only weak passwords are rejected; legitimate changes satisfy the 10-char signup
  policy users already passed at register.
- **Evidence:** audit/evidence/phase2/a4-guest-auth-map.log (validatePassword usage sweep); a4-validation-matrix.md row 58.
